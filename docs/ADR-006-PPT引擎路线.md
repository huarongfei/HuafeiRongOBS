# ADR-006：PPT 实时渲染引擎路线

- 状态：**待决策（等你确认路线）**
- 日期：2026-09-25
- 相关：`docs/PPT-方案.md`、`docs/ADR-记录.md`（ADR-001..005）

## 1. 需求（你这次明确提出）
1. **实时渲染**：动画（进入/退出/强调/路径）、幻灯片切换必须**按帧驱动**，而不是"每页一张静态图"
2. 可接受：**自研 PPT 引擎**，或**改开源**（fork 后按我们需求魔改）
3. 已有的产品约束不变：多画布多输出、每画布独立录制/推流、讲者视图、Windows 10/11、中文优先

## 2. 已实测事实（决定了哪些路走不通）
| 方案 | 实测结论 | 证据 |
|---|---|---|
| 进程内 LibreOfficeKit（LOK）`lok_preinit_2` | init 成功，`documentLoad` 于 mergedlo 内部 AV 0xC0000005 | OBS 进程 + 独立 .NET 进程均复现 |
| 进程内 LOK 官方入口 `libreofficekit_hook_2`（dlopen + PATH + 正确 install_path） | **在 hook 内部即 AV**，LO 日志都未初始化 | 独立进程复现，进度打点证明死在 hook 调用内 |
| soffice 转 PDF + 进程内 pdfium 渲染（当前已实现） | ✅ 可用、稳定、内嵌字体、矢量清晰 | 隔离验证 `pages=2, nonWhite=16.58%` |
| soffice 一次性转换 | ✅ 可用，转换后进程退出（无常驻桥） | 已用于生成 test-slides.pptx / 转 pdf |

**结论**：stock 版 LibreOffice 在 Windows 上**不支持进程内嵌入**（LOK 官方定位 Linux，Windows 版为实验性）。
"改开源 = 改 LibreOffice" 这条路，除非我们自己编译 LO 并重写它的 Windows 嵌入层，否则拿不到**进程内实时帧**。

## 3. 三条候选路线

### 路线 A：自研原生 GPU 引擎（HFR Slides Engine）
- **做法**：自己解析 OOXML（pptx），构建场景图，用 OBS 的图形栈（D3D11/gs）+ DirectWrite 渲染；动画由 OBS 帧时钟驱动
- 保真来源：ECMA-376 规范 + 主题/母版/版式继承 + DirectWrite 文本排版
- **优势**
  - 真·实时：动画/切换是引擎里的时间轴，可暂停、跳页、逐帧、任意速度
  - **与我们的差异化天然契合**：多画布 = 同一份演示可让不同输出**处于不同页/不同动画进度**
  - 零外部依赖、零 AGPL 传染、随包体积小（无 1.5GB LO 运行时）
  - 与 OBS 合成管线同源：可直接做出" PPT 图层参与滤镜/转场/色键 "
- **代价**
  - 完整 fidelity 是长期工程（PowerPoint 的排版/字体度量/效果细节极多）
  - 需要自建：文本度量与换行（DirectWrite）、表格、渐变、阴影、3D/艺术字（可降级）
- **工作量**：第一阶段可用（静态 + 基础动画）约 **4~8 周**；"常见商务模板 95% 视觉可接受"约 **3~6 个月**；完全对齐 PowerPoint 属多年目标

### 路线 B：fork OnlyOffice 的 sdkjs（浏览器内核）挂 WebView2
- **做法**：把 OnlyOffice 的演示文稿编辑器 JS 内核（`sdkjs`，AGPLv3）塞进 WebView2，OBS 侧抓帧
- **优势**：自带成熟的 pptx 渲染 + 动画 + 切换；起步快
- **代价**：AGPLv3（我们当前 GPL-2.0 产品要非常小心，法务风险高）；体积与内存大；抓帧进 OBS 有延迟与色彩/同步问题；与 OBS 图形栈隔离（没法参与滤镜链）；离线可用性要自己兜
- **工作量**：集成 2~4 周；法务与稳定性风险高

### 路线 C：混合（推荐落地形态）
- **主渲染 = 路线 A 自研引擎**（实时动画）
- **兜底烘焙 = 现有 soffice→PDF/pdfium**：导入时把**引擎暂不支持的节点**（复杂图表/SmartArt/3D/异体字排版）离线烘成位图，作为该节点的高清贴图
- 效果：**常见模板 100% 有画面**，动画实时；不支持的局部降级为"静态但正确"
- 另：保留 pdfium 路径作为"整页兜底模式"（演示前一天救场用）

## 4. 推荐
**路线 C（自研引擎为主 + soffice 烘焙兜底）**，理由：
1. 实时动画只有自研引擎能拿到帧级控制；
2. 多画布多输出的产品定位（不同屏幕不同页/不同进度）是自研才能做的差异化；
3. 免 AGPL、免 1.5GB 运行时、免 WebView2；
4. 有烘焙兜底，**不会出现"打不开的 deck"**，风险可控、可增量交付。

## 5. 分期里程碑（建议）
| 阶段 | 目标 | 交付判据 | 预估 |
|---|---|---|---|
| **M0 尖刺** | 解析 pptx + 用 OBS 图形栈渲染 1 页（文本/图片/形状/纯色填充）到纹理 | 1080p60 下余量 ≥ 40%，中文文本正确换行 | 3~5 天 |
| **M1 静态保真** | 主题/母版/版式继承、文本框 autofit、表格、渐变/描边/圆角、旋转/翻转、组合；不支持节点走 soffice 烘焙 | 20 套真实模板人工比对，≥ 95% 页"视觉可接受" | 2~4 周 |
| **M2 实时动画** | `p:timing` SMIL 子集（进入/退出/强调/路径、顺序/并行/触发）、`p:transition` 切换；OBS 帧时钟驱动 | 逐帧可控、可暂停/回退；切换无撕裂 | 2~4 周 |
| **M3 多输出与媒体** | 每画布独立时间轴（同一 deck 不同页/进度）、内嵌音视频接 OBS media source、讲者视图备注与下一页、翻页笔 | 3 块屏各播不同页不互相干扰 | 2~3 周 |
| **M4 性能与兼容** | 字形图集、2× 超采样、增量排版、缺字体报告与替换表、4K | 4K30 稳定；缺字体可见提示 | 2~3 周 |

## 6. 风险与对策
| 风险 | 对策 |
|---|---|
| 文本度量与 PowerPoint 不一致 | DirectWrite + 记录差异样本集，做逐模板回归；提供"行距/字号微调"高级选项 |
| 字体缺失 | 随包 CJK 字体 + 缺字体报告 + 替换表（延续 `docs/PPT-方案.md` 策略） |
| 复杂效果做不出 | 走**烘焙兜底**（soffice 离线渲染该页/该节点） |
| 解析器与规范偏差 | 以 ECMA-376 + 真实素材回归；解析失败必落到烘焙 |
| 工期 | 分期交付：M0/M1 先能用，M2 起才有"实时"卖点 |

3. 是否同意把现有"整页 PDF 模式"保留为可切换的兼容模式（演示前保命用）？
